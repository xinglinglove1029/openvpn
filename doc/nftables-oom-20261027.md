# 2026-10-27 OpenVPN 反复掉线与 nftables 内存耗尽

## 生产证据

野草云 4GB 主机在 10 月 26 日夜间至 27 日凌晨多次出现 global OOM，内核日志记录大量 nft 子进程，每个占用约 200MB。OpenVPN 容器 OOMKilled=true，重启主机后容器没有自动启动（原策略为 no）。Rocky / iStoreOs 日志出现服务端连接重置、ping-restart 和持续 TLS 握手超时。

持久化 openvpn.nft 文件有 393237 行、11993443 字节，单条 IPv4 黑名单规则重复 196608 次。

## 原因与修复

启动函数 load_nftconfig 直接执行 nft -f，将保存的规则追加到已经存在的应用表。上下线 hook 保存整张表后，下次重启又追加这些重复规则。表不断放大，加上没有并发和超时限制的 nft 查询，最终耗尽主机内存。

- Docker 和原生 Linux 入口均按链去重旧快照，并在一个 nft 事务中替换应用自己的表；保留其他表，错误配置不会清空有效规则。
- 应用内 nft 子进程共用单一执行槽，排队与执行最多 5 秒，输出最多 4MB。
- 快照保存串行执行，并通过临时文件和原子重命名发布；没有关联防火墙策略的上下线事件不再导出全表。
- Compose 使用 unless-stopped，使主机重启后自动恢复服务。
- 撤回按 ROUTING_TABLE Last Ref 超过 90 秒隐藏在线客户端的逻辑：业务空闲不等于会话断开，CLIENT_LIST 才是会话来源。

## 回归验证

scripts/test-nft-reload.sh 必须在隔离网络命名空间中执行。测试先保存带重复规则和黑名单地址的快照，然后反复加载、保存，检查规则数量不增长，黑名单地址及无关表保留；最后以错误配置验证原子回滚。CI 分别验证 Docker 和原生入口。

旧实现第一次重载产生 6 条重复规则；修复后始终保留 1 条。进程测试验证并发串行化、排队超时、杀掉卡住的子进程后释放执行槽，以及输出大小限制。
